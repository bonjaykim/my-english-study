Escalation on a Factory Reset Boot Loop Nine Days before the Pulse Watch Launch

Pulse Watch 출시 9일 전, 공장 초기화 후 부트 루프 긴급 점검

Symptom and Scope

08 · Nari ChoiSQE

Here's what we know. On the LTE variant only, if the user activates an eSIM profile and then performs a factory reset, the watch gets stuck in a boot loop. It shows the logo, restarts after about forty seconds, and after five attempts it drops into recovery mode and asks the user to wipe data again. Wiping again doesn't help, because the eSIM profile lives in a separate secure chip and survives the reset.

09 · Sarah LimProgram Management

How often does it happen? Is this every device, or a percentage?

10 · Nari ChoiSQE

It's not every device. We ran the sequence two hundred times across forty units. It reproduced thirty-one times, so roughly fifteen percent per attempt. Once a device gets into the loop, though, it stays there. We've only been able to recover them with a service tool that clears the eSIM profile, which a normal user doesn't have.

11 · Jason KwonSQE

I want to be precise about the scope, because it matters for the decision. The out-of-box experience is not affected. A brand-new watch has no eSIM profile, so the first boot is completely clean. The problem only appears after the user has activated a profile and then resets the watch. Wi-Fi-only models are not affected at all.

12 · Sarah LimProgram Management

That's an important distinction. What share of launch units are LTE?

13 · Jason KwonSQE

About thirty-five percent of the initial shipment, and it's concentrated in North America and Korea, where the carriers are promoting it heavily. So it's not a small population.

Root Cause Analysis Status

14 · Sarah LimProgram Management

Alex, Mina, what do the logs tell us about why it loops?

15 · Mina HwangPlatform Framework

From the boot side, the picture is fairly clear. Each boot, the system server starts, and within thirty seconds, it crashes. The crash is in the eSIM provisioning service, which runs inside the system server. Because the system server crashes repeatedly during boot, the rescue logic concludes the device is unrecoverable and escalates to recovery mode. So the rescue logic is doing exactly what it was designed to do. The real question is why the provisioning service crashes.

16 · Alex YooPlatform Framework

And that's where I come in. After a factory reset, the provisioning service finds an existing profile on the secure chip and tries to restore it. To do that, it asks the modem for the profile's network configuration. On a clean boot, the modem is usually ready about twelve seconds after the system server starts. But in the failing cases, the request goes out before the modem has finished initializing, the response comes back empty, and the service dereferences a null object. It's an uncaught exception, and because it's in the system server, it takes the whole process down.

17 · Sarah LimProgram Management

So it's a timing race between the provisioning service and the modem. Why didn't we see it before this week?

18 · Dongwook KangKernel & BSP

I think I can answer that one. Two weeks ago, we merged a boot time optimization in the BSP that starts the system server about six seconds earlier. It was part of the push to get the watch below twenty seconds of boot time. The modem initialization didn't move, so we effectively narrowed the gap between the two. Before that change, the modem was always ready in time.

19 · Jason KwonSQE

That matches our data. The first build where Nari can reproduce the loop is the one with the boot time change. We tested two builds before it, and both are clean in a hundred attempts.

20 · Mina HwangPlatform Framework

I'd add one thing. Even though the boot change exposed it, the underlying bug is the missing null check and the missing retry logic in the provisioning service. It was always fragile. We just got lucky with the timing until now.

Fix Options

21 · Sarah LimProgram Management

Okay. I hear two possible fixes. One, revert the boot time change. Two, fix the provisioning service properly. Let's go through the pros and cons of each, with an eye on Friday's golden build.

22 · Dongwook KangKernel & BSP

The revert is the safest option in terms of code risk. It's a well-understood change, and we've shipped without it for months. The downside is that boot time goes back up to about twenty-six seconds, and marketing has already used the 'under twenty seconds' claim in launch materials.

23 · Sarah LimProgram Management

I'll be honest, that's a conversation I'd rather not have with marketing nine days before launch. But I'd have it if it's the right call. Alex, what about the proper fix?

24 · Alex YooPlatform Framework

The proper fix has three parts: a null check on the modem response, a retry with backoff until the modem reports ready, and catching exceptions inside the restore path so a failure there can never take down the system server. I have a draft already. The code is maybe sixty lines. Testing is the bigger question, because this path runs on every boot of every LTE device.

25 · Jason KwonSQE

From SQE's perspective, I'm uncomfortable putting a sixty-line change into a code path that runs on every boot, two days before golden. Not because I doubt Alex, but because we wouldn't have time to run the full regression suite. We'd be shipping a change to millions of devices with maybe one day of testing.

26 · Alex YooPlatform Framework

I understand the concern, but I'd argue the revert has its own risk. If we revert the boot change, the provisioning bug is still there. It's just hidden again. Any future change that shifts boot timing, or a slower modem firmware update from the carrier, could bring it right back, and next time it might be in the field.

27 · Mina HwangPlatform Framework

Could we do both, but in different builds? Revert the boot change for the golden factory build, so what goes into the box is proven and safe. Then put the proper provisioning fix, plus the boot optimization, into the day-one update, after it has gone through the full regression suite next week.
