Diagnosing System Server Freezes Caused by Binder Thread Exhaustion

binder 스레드 고갈로 인한 시스템 서버 멈춤 원인 분석

Orion Lite에서 화면이 약 1분간 멈춘 뒤 소프트 리부트되는 문제가 야간 앱 자동 업데이트 시간대에 집중적으로 보고되었습니다. SQE, 플랫폼 프레임워크, 커널·BSP, 개발자 관계 팀이 덤프에서 확인한 binder 스레드 고갈, 저장 공간 부족 단말의 느린 I/O, 서드파티 런처 앱의 과도한 호출이 겹친 원인과 대응 방안을 논의합니다.

03 · Brian ShinPlatform Framework

Brian, Framework lead. I'm here because whatever we decide will probably touch the package manager, which is my team's code.

04 · Yuna KwakKernel & BSP

Yuna, Kernel and BSP. Soyeon mentioned slow storage, so I'm here for the file system side.

05 · Lisa HanDeveloper Relations

Lisa Han, Developer Relations. I manage our relationships with the major app developers, so if we need one of them to change something, I'm the one who makes the call.

The Symptom

06 · Soyeon ParkSQE

Here's what users report. The phone freezes completely for about a minute, usually in the early morning, and then it shows the boot animation and restarts. Users who are awake often notice it while their alarm is about to ring, which is how it became visible on social media. A few people said their alarm didn't go off.

07 · Brian ShinPlatform Framework

A missed alarm is a serious problem for users, even if the freeze is short. What does the field data show about timing?

08 · Soyeon ParkSQE

About seventy percent of the events happen between 2 a.m. and 6 a.m. local time, which is when the app store runs automatic updates while the phone is charging. The rate is about 0.4 percent of Orion Lite devices per week, and it's roughly three times higher on devices with less than ten percent free storage.

09 · Elena ParkPlatform Framework

Do we know whether it happens on Orion as well, or only Orion Lite?

10 · Soyeon ParkSQE

Orion has it too, but about eight times less often. Orion Lite has slower storage and less memory, which seems to matter.

What the Dumps Show

11 · Soyeon ParkSQE

Elena, can you walk us through the dumps?

12 · Elena ParkPlatform Framework

Sure. I used the order Yuna described at the tech share three weeks ago. The reset reason is the system server watchdog. The main thread of the system server is blocked waiting for a binder reply. When I looked at the system server's binder thread pool, all thirty-one threads were busy. Not one was free to handle new requests, so every incoming call, including the one from the main thread, just waited.

13 · Yuna KwakKernel & BSP

What were the thirty-one threads doing?

14 · Elena ParkPlatform Framework

Twenty-seven of them were waiting on the same lock inside the package manager. Three were handling unrelated requests normally. And one thread was holding the lock while writing package information to storage. That write had been in progress for over forty seconds.

15 · Brian ShinPlatform Framework

Forty seconds for a write? That's absurd. The package information file is usually a few megabytes.

16 · Yuna KwakKernel & BSP

On a nearly full device, it's not absurd at all, unfortunately. When the file system has very little free space, it has to run garbage collection before it can write new data, moving existing blocks around to free up room. On slower storage, like Orion Lite's, that can take tens of seconds, and the writing thread is blocked the whole time.

17 · Elena ParkPlatform Framework

That explains the storage correlation. But there's one more piece. The twenty-seven waiting threads were almost all serving the same app: a popular third-party launcher. It was calling the package manager repeatedly to rebuild its app list.

The Third-Party Launcher

18 · Lisa HanDeveloper Relations

Which launcher is it? I may already have a contact there.

19 · Elena ParkPlatform Framework

It's one of the top three launchers on our store, with several million installs on Orion Lite. Every time any app is installed or updated, the system sends a broadcast. This launcher reacts by querying the full list of apps, not once, but once for each of several categories, about twenty calls in total. During the night, when dozens of apps update in a row, it generates hundreds of calls in a few minutes.

20 · Brian ShinPlatform Framework

Normally, those calls are fast, so it doesn't matter. But if they arrive while the package manager lock is held for forty seconds, every one of them grabs a binder thread and waits. Within seconds, the pool is exhausted.

21 · Lisa HanDeveloper Relations

So the launcher isn't doing anything forbidden; it's just inefficient. That matters for how I approach the developer. If I tell them their app is crashing our phones, they'll be defensive. If I tell them their app is making excessive calls and show them a better pattern, they'll usually fix it.

22 · Elena ParkPlatform Framework

Exactly. And to be fair to them, our documentation doesn't warn against this pattern. The better approach is to listen for the specific package that changed and update only that entry, instead of rebuilding everything.

Three Layers, Three Fixes

23 · Soyeon ParkSQE

So we have three layers: a nearly full device makes writes slow, the package manager holds a lock during a slow write, and an app floods the system with calls during that window. Which ones do we fix?

24 · Brian ShinPlatform Framework

The one we fully control, and the one that matters most, is the lock. The package manager shouldn't hold its main lock while writing to storage. The usual pattern is to take a snapshot of the data under the lock, release the lock, and then write the snapshot to disk. Then a slow write only delays the write, not every query.

25 · Elena ParkPlatform Framework

I checked, and the newer Android version already does exactly that. It was changed upstream about a year ago. Orion Lite's framework is based on the older version, so it doesn't have the change. Backporting it is possible, but the package manager is one of the most sensitive parts of the system. A mistake there could corrupt the package database.

26 · Yuna KwakKernel & BSP

From the storage side, there's something we can do independently. We can make the file system start background garbage collection earlier when free space is low, during idle time, so that space is already prepared when a write arrives. It doesn't eliminate slow writes, but in our tests, it cuts the worst case from forty seconds to under ten.

27 · Brian ShinPlatform Framework

Under ten seconds would be enough to avoid the watchdog in almost every case. The watchdog fires at sixty seconds, and the binder pool would recover once the lock is released.

28 · Lisa HanDeveloper Relations

And on the app side, I can contact the launcher developer next week. If they ship a fix within a month, that removes the flood for millions of users, on every device, not just ours.

Choosing the Approach

29 · Soyeon ParkSQE

Let's be concrete about risk and timing. Orion Lite's next release, 1.4.0, has its content cutoff on September 3rd, after Grace moved it. What can realistically make that?

30 · Yuna KwakKernel & BSP

The file system tuning is a configuration change plus a small kernel patch that's already upstream. I can have it ready on Monday, and the storage stress profile can validate it by Wednesday.

31 · Elena ParkPlatform Framework

The package manager backport is a different story. Even if I start today, I wouldn't want it in a release without at least two weeks of testing, including upgrade testing with real user data. That means 1.5.0 in October at the earliest.

32 · Brian ShinPlatform Framework

Is there a smaller framework change we could make for 1.4.0? For example, limiting how many binder threads a single app can occupy at once. If the launcher could use at most eight threads, the other twenty-three would stay free for the system.

33 · Elena ParkPlatform Framework

That's an interesting idea, but I'd be careful. A per-app limit changes the behavior for every app, including well-behaved ones that legitimately make parallel calls. We could easily cause slowdowns elsewhere. I'd rather not introduce that kind of global change in a maintenance release.

34 · Soyeon ParkSQE

Then the plan is: file system tuning in 1.4.0 as the immediate mitigation, the package manager fix in 1.5.0 as the real fix, and Lisa working with the launcher developer in parallel. Does anyone disagree?

35 · Brian ShinPlatform Framework

No disagreement. I'd only add that the alarm issue deserves its own look.

The Missed Alarm

36 · Brian ShinPlatform Framework

Even if the freeze becomes rare, a soft reboot at the wrong moment can still swallow an alarm. That's the part users are angriest about. Shouldn't the alarm survive a system server restart?

37 · Elena ParkPlatform Framework

It should, and normally it does. Alarms are stored persistently and rescheduled at boot. But if the restart happens within a minute of the alarm time, the alarm is rescheduled for a time that has already passed, and the current logic treats it as missed rather than firing it late.

38 · Soyeon ParkSQE

That sounds like a separate bug that's worth fixing regardless of the freeze. An alarm that's two minutes late is far better than no alarm at all.

39 · Elena ParkPlatform Framework

Agreed. If an alarm's time passed less than ten minutes ago when the system restarts, it should fire immediately. That's a small, contained change in the alarm service, and I think it can make 1.4.0.

Other Models and Atlas

40 · Brian ShinPlatform Framework

Let's check our exposure beyond Orion Lite. Orion has the same framework version, so it has the same lock problem. It's just less visible because its storage is faster. Should the file system tuning go into Orion's next build as well?

41 · Yuna KwakKernel & BSP

I'd say yes, but in October, not as an exception. Orion's September build is already locked and submitted, and the rate on Orion is low enough that a month's wait is reasonable. I'll make sure the change goes into the common kernel branch, so it reaches both products.

42 · Elena ParkPlatform Framework

For Atlas and Atlas Lite, the package manager already has the newer locking from the upstream framework, so the main risk is gone. But Atlas Lite will ship with only four gigabytes of memory in some markets, and its storage is a cost-reduced part. I'd want the same overnight update scenario in its test plan from the start.

43 · Soyeon ParkSQE

I'll pass that to Nina for the Atlas Lite test plan. It fits nicely with the memory pressure tests she's already defining.

44 · Lisa HanDeveloper Relations

And the launcher developer's fix, if they make one, helps every device at once, including the new ones. That's another reason to approach them constructively.

Detecting This Earlier

45 · Brian ShinPlatform Framework

This issue has probably existed for a long time, getting worse as devices filled up. Why did it take two weeks of field reports for us to notice?

46 · Soyeon ParkSQE

Two reasons. First, our test devices are almost never full. We reset them often, so they rarely have less than half of their storage free. Second, the freezes happen at night, when nobody is watching, and a soft reboot doesn't show up as a crash in our main dashboard. It shows up as a watchdog event, which we only review weekly.

47 · Yuna KwakKernel & BSP

Then we should keep a group of test devices deliberately filled to ninety percent or more, and leave them that way. Real users live with nearly full phones for months. Our lab devices should too.

48 · Elena ParkPlatform Framework

And watchdog restarts should be on the main dashboard, next to crashes, with the same alert thresholds. From the user's point of view, a minute-long freeze followed by a restart is worse than most crashes.

49 · Soyeon ParkSQE

Agreed on both. I'll set up a group of twenty full devices in the stress lab next week, and ask Kyle to add watchdog restarts to the main field dashboard.

50 · Brian ShinPlatform Framework

That's a cheap change with a big payoff. Thank you. Let's review the first week of data from the full devices at our next check-in.

Validation Plan

51 · Soyeon ParkSQE

For validation, I'd like to reproduce the original scenario in the lab, not just test each fix separately. We can fill test devices to ninety-five percent storage, install the same launcher, and trigger fifty app updates in a row while the device is charging with the screen off.

52 · Yuna KwakKernel & BSP

Please measure the longest package manager write in each run as well. That tells us directly whether the file system tuning is doing its job, even if the freeze doesn't happen.

53 · Elena ParkPlatform Framework

And for the alarm fix, a simple test: schedule an alarm, force a system server restart thirty seconds before it, and check that it fires within a minute of the original time.

Action Items and Closing

54 · Soyeon ParkSQE

Let me summarize. Yuna: file system garbage collection tuning, ready Monday, validated by Wednesday. Elena: the alarm catch-up fix for 1.4.0, and start the package manager backport for 1.5.0. Lisa: contact the launcher developer next week with the data and a recommended pattern. Brian: add a warning about this pattern to our developer documentation. And SQE will build the full reproduction scenario and validate everything together.

55 · Lisa HanDeveloper Relations

I'll send the developer a sample of the call pattern from the dumps, anonymized, so they can see exactly what their app is doing. I'll also offer them early access to our test devices with nearly full storage, so they can reproduce the problem themselves and verify their fix before it ships.

56 · Elena ParkPlatform Framework

That's a great idea. Developers fix things much faster when they can see the problem on their own desk.

57 · Yuna KwakKernel & BSP

I'll share the file system tuning patch with the upstream maintainers as well, along with our measurements. If they find it useful, other device makers with slower storage will benefit too.

58 · Soyeon ParkSQE

Thank you, everyone. Our next check-in is Wednesday, September 2nd, at 10 a.m. Korea time, the day before the 1.4.0 cutoff. By then, I'd like to see the reproduction results with Yuna's tuning, the alarm test, and a first reply from the launcher developer, if we have one.

59 · Brian ShinPlatform Framework

Thanks, Soyeon. This was a good example of the triage order from the tech share paying off. Three weeks ago, a dump like this would have bounced between teams for days.

03 / Business expressions

my daily bread

제 일상 업무 · 늘 하는 익숙한 일이라고 가볍게 말할 때

System server hangs are my daily bread, so I've already looked at the dumps.

응용 연습
Kernel crash dumps are my daily bread.

makes the call

연락하다; 결정을 내리다 · 외부 파트너에게 직접 연락하는 역할을 말할 때

I manage our relationships with the major app developers, so if we need one of them to change something, I'm the one who makes the call.

응용 연습
If we need the vendor's CTO, the program director makes the call.

seems to matter

중요한 요인으로 보인다 · 상관관계가 있어 보이는 조건을 말할 때

Orion Lite has slower storage and less memory, which seems to matter.

응용 연습
The ambient temperature seems to matter.

not one was free

단 하나도 비어 있지 않았다 · 자원이 완전히 고갈된 상태를 강조할 때

Not one was free to handle new requests, so every incoming call, including the one from the main thread, just waited.

응용 연습
All the test devices were booked; not one was free.

That's absurd

말도 안 된다 · 예상과 크게 다른 수치에 놀랄 때

That's absurd.

응용 연습
Ten minutes to boot? That's absurd.

not absurd at all, unfortunately

안타깝게도 전혀 말이 안 되는 게 아니다 · 상대가 놀란 수치가 실제로 가능함을 설명할 때

On a nearly full device, it's not absurd at all, unfortunately.

응용 연습
On an old SD card, that delay is not absurd at all, unfortunately.

in a row

연달아 · 같은 일이 연속으로 일어날 때

During the night, when dozens of apps update in a row, it generates hundreds of calls in a few minutes.

응용 연습
The test failed three times in a row.

doing anything forbidden

금지된 걸 하는 · 규칙 위반은 아니지만 문제를 일으키는 경우를 구분할 때

So the launcher isn't doing anything forbidden; it's just inefficient.

응용 연습
The app isn't doing anything forbidden, but it drains the battery.

be defensive

방어적으로 나오다 · 외부 파트너가 비난을 받으면 보일 반응을 예상할 때

If I tell them their app is crashing our phones, they'll be defensive.

응용 연습
If we lead with blame, the vendor will be defensive.

to be fair to them

그들을 위해 공정하게 말하자면 · 상대의 입장을 균형 있게 고려할 때

And to be fair to them, our documentation doesn't warn against this pattern.

응용 연습
To be fair to them, the spec changed after they shipped.

a different story

전혀 다른 이야기 · 앞의 경우와 상황이 크게 다를 때

The package manager backport is a different story.

응용 연습
Fixing the config is easy; redesigning the driver is a different story.

at the earliest

빨라야 · 가장 이른 가능 시점을 말할 때

That means 1.5.0 in October at the earliest.

응용 연습
The vendor fix will arrive next Friday at the earliest.

well-behaved ones

잘 동작하는 것들 · 규칙을 잘 지키는 앱이나 구성 요소를 구분할 때

A per-app limit changes the behavior for every app, including well-behaved ones that legitimately make parallel calls.

응용 연습
The new limit shouldn't penalize well-behaved apps.

swallow an alarm

알람을 삼키다(울리지 않게 하다) · 중요한 이벤트가 사라지는 상황을 생생하게 표현할 때

Even if the freeze becomes rare, a soft reboot at the wrong moment can still swallow an alarm.

응용 연습
A crash during the update could swallow the notification.

far better than

~보다 훨씬 나은 · 차선책이 최악보다 훨씬 나음을 강조할 때

An alarm that's two minutes late is far better than no alarm at all.

응용 연습
A slow fix is far better than no fix.

doing its job

제 역할을 하는 · 조치가 의도대로 효과를 내는지 확인할 때

That tells us directly whether the file system tuning is doing its job, even if the freeze doesn't happen.

응용 연습
The new metric shows the cache is doing its job.
