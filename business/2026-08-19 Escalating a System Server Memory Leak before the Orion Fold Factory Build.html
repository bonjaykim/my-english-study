Escalating a System Server Memory Leak before the Orion Fold Factory Build

Orion Fold 팩토리 빌드 직전 시스템 서버 메모리 누수 긴급 점검

9월 18일 출시를 앞둔 Orion Fold에서, 접고 펼 때마다 시스템 서버 메모리가 조금씩 늘어나 수천 번 후 소프트 리부트가 발생하는 누수가 발견되었습니다. 8월 28일 팩토리 빌드 마감을 앞두고 프로그램 관리, SQE, 플랫폼 프레임워크, 디스플레이 소프트웨어 팀이 원인 분석 현황과 수정 일정, 대안을 논의합니다.

Opening and Context

Good morning, everyone. I'm Sarah, and as most of you know, I've moved from the Pulse Watch launch straight onto Orion Fold. We're thirty days from launch and nine days from the factory build cutoff on August 28th. I called this meeting because SQE found a memory leak over the weekend that could be a launch blocker, and I want a clear plan by the end of this hour.

02 · Hyemi SongSQE

Hyemi, SQE lead for Orion Fold. Before we get to the leak, a quick piece of good news: the hard lockup fix from last week is holding up. We've run twenty-two thousand folds on the robots with the fix, and we've had zero freezes.

03 · Jisu HanDisplay Software

That's a relief. The access timeout dumps pointed exactly at the interrupt handler, so we were fairly confident, but it's good to see it confirmed at scale.

04 · Brian ShinPlatform Framework

Brian from Platform Framework, and Taemin from my team, who's been looking at the heap dumps since Sunday.

05 · Taemin KoPlatform Framework

Hi. Taemin Ko, Framework. I work on window management and multi-display support.

06 · Woojin ChoiDisplay Software

Woojin, Display Software. I suspect part of this leak may end up in our area, so I'm glad to be here early.

The Symptom

07 · Sarah LimProgram Management

Hyemi, what did you find?

08 · Hyemi SongSQE

Because the robots now run for days without freezing, we were able to see a much slower problem for the first time. The system server's memory grows by about one point two megabytes every time the device is folded or unfolded, and it never comes back down. After roughly two thousand folds, the system server reaches its memory limit, the low memory killer terminates it, and the device does a soft reboot: the screen goes black, the boot animation plays, and everything restarts in about twenty seconds.

09 · Sarah LimProgram Management

Two thousand folds sounds like a lot. How long would that take for a real user?

10 · Hyemi SongSQE

Based on our usage studies from the previous foldable, the median user folds about eighty times a day, and heavy users fold up to two hundred times. So a median user would hit it after about twenty-five days without a reboot, and a heavy user after ten. Most people restart their phones less often than that, so in practice, many users would see a random restart every few weeks.

11 · Brian ShinPlatform Framework

And a soft reboot loses whatever the user was doing, which reviewers will notice in their long-term reviews. It's not as dramatic as a freeze, but it's a launch blocker in my view.

Heap Analysis So Far

12 · Sarah LimProgram Management

Taemin, what do the heap dumps show?

13 · Taemin KoPlatform Framework

There are actually two separate leaks, and they add up to the one point two megabytes. The first one is in managed memory, the Java heap. It's about two hundred kilobytes per fold. Every fold creates a new configuration listener for the taskbar feature on the main screen, and the old listener is never unregistered. So we accumulate thousands of listeners, and each one holds a reference to a full display configuration object.

14 · Brian ShinPlatform Framework

That's a textbook leak, and the good news is that the fix is simple. Taemin already has a patch that unregisters the listener when the main display turns off. It's been tested on two robots since yesterday, and the managed heap stays flat.

15 · Sarah LimProgram Management

And the second leak?

16 · Taemin KoPlatform Framework

The second one is in native memory, and it's the bigger one: about one megabyte per fold. The heap dump tools don't show native allocations in as much detail, but what we can see is that the graphics buffer count grows with each fold. It looks like the surfaces used to draw the cover screen aren't being fully released when the cover display turns off.

17 · Woojin ChoiDisplay Software

That's where it crosses into our area. When the cover display turns off, the display driver releases its own buffers, but the composition layer for that display is supposed to be destroyed by the framework. If the framework keeps a reference to the layer, the buffers attached to it stay allocated, even though nothing is ever drawn to them again.

18 · Jisu HanDisplay Software

Is it possible the managed leak and the native leak are actually the same bug? If the old listeners hold references to display configuration objects, and those objects hold references to the layers, then fixing the listener leak might also release the buffers.

19 · Taemin KoPlatform Framework

That was my first hope too, but no. With my patch, the managed heap stays flat, but the native memory still grows by about one megabyte per fold. So they're independent. The layer must be held by something else.

Narrowing Down the Native Leak

20 · Sarah LimProgram Management

How do we find out what's holding it?

21 · Woojin ChoiDisplay Software

The compositor keeps a list of every layer with its owner and reference count. If we dump that list after, say, a hundred folds, we should see a hundred cover screen layers that should have been destroyed, and the dump tells us which process created them. That narrows it down to one owner in a few minutes.

22 · Hyemi SongSQE

I can run that today. One robot, a clean boot, a hundred folds, then the layer dump. I'll have it to you by early afternoon.

23 · Taemin KoPlatform Framework

One suspicion I have: the always-on display on the cover screen. When the device is unfolded, the cover screen turns off, but the always-on clock has its own layer that might be recreated each time instead of reused. That feature was added late, in July.

24 · Brian ShinPlatform Framework

That's a good lead. Late features are where leaks usually hide, because they get the least soak time. If it's the always-on clock, that's my team's code, and the fix would likely be to reuse a single layer.

25 · Hyemi SongSQE

I can test that theory quickly too. If I turn off the always-on display on the cover screen and run a hundred folds, and the native memory stays flat, we'll know. I'll run both tests in parallel on two robots, so we get both answers at the same time instead of one after the other.

Schedule and Options

26 · Sarah LimProgram Management

Let's talk about time. The factory cutoff is August 28th. If we find the native leak today, can both fixes be in the factory build?

27 · Hyemi SongSQE

For me to sign off on a leak fix, I need a long soak: at least five thousand folds on several robots, to prove the memory stays flat well past the two-thousand-fold point. At our current robot speed, that's about five days. So if a fix is ready by Friday the twenty-first, the soak finishes on the twenty-sixth, which leaves two days of margin.

28 · Sarah LimProgram Management

And if the native fix isn't ready by Friday?

29 · Brian ShinPlatform Framework

Then I see two options. Option one: ship the factory build with only the managed leak fixed, and put the native fix in the day-one update. A brand-new device can't reach two thousand folds in its first week, so as long as users take the day-one update, they'd never hit the problem. Option two: a mitigation in the factory build that destroys and recreates the whole cover screen composition when the display turns off. It's heavy-handed, but it releases everything.

30 · Woojin ChoiDisplay Software

I'd be cautious about option two. Recreating the whole composition on every fold adds latency to the unfold animation, maybe fifty to eighty milliseconds. Users would feel that, and the fold animation is one of the first things reviewers judge. I'd rather not trade a slow leak for a visibly slower fold.

31 · Sarah LimProgram Management

Understood. So option one is our fallback. Given what we learned on Pulse Watch, I'm comfortable with a day-one update as part of the plan, as long as it's planned from the start rather than added in a panic.

32 · Hyemi SongSQE

One condition from SQE: if we go with option one, the day-one update must be available before the first customer units ship, and we need the same companion check we used on Pulse Watch, so setup encourages the update.

Day-One Update Logistics

33 · Sarah LimProgram Management

Since the day-one update is now part of the plan either way, let's talk about logistics. On Pulse Watch, we learned that the update has to be ready before customer units arrive, and that some markets skip Wi-Fi during setup. What's different for Orion Fold?

34 · Hyemi SongSQE

The biggest difference is carriers. Orion Fold is sold mainly through carriers, and several of them require approval for any update, including a day-one update. The carrier certification build is the factory build, so if the native fix goes into a day-one update, it needs a separate, fast approval from each carrier before launch day.

35 · Sarah LimProgram Management

How long do carriers usually need for a day-one update?

36 · Hyemi SongSQE

Ryan from my team says most carriers can review a small delta update in five to seven working days, if we tell them in advance that it's coming. The two US carriers that are usually slowest want at least ten. So if we submit the day-one update by September 3rd, we should have approvals before the eighteenth.

37 · Brian ShinPlatform Framework

That gives us a hard deadline for the native fix even in the fallback case. If we can't fix it by Friday for the factory build, we still need it done, soaked, and submitted by September 3rd. That's two extra weeks, which should be plenty, but it isn't open-ended.

38 · Woojin ChoiDisplay Software

One more consideration. Review units for journalists usually ship about two weeks before launch, so around September 4th. Those units will run the factory build. If the native fix isn't in it, reviewers who use the device for a long-term review could hit the soft reboot after a few weeks, unless they install the update.

39 · Sarah LimProgram Management

Good point. After Nova Tab, I'm not going to rely on reviewers following instructions. If we end up in the fallback case, I'll ask the review program team to flash the day-one update onto review units before they ship. It's manual work, but for a few hundred units, it's worth it.

40 · Taemin KoPlatform Framework

That makes me even more motivated to have the fix ready by Friday. It would save everyone a lot of work.

Preventing Similar Leaks

41 · Sarah LimProgram Management

How did we miss this until three weeks before launch? I'm not looking for blame, but I need to explain it to the launch director.

42 · Hyemi SongSQE

Honestly, the hard lockup hid it. Until last week, the robots froze every few hundred folds, so no device ever ran long enough to reach two thousand folds. Fixing one bug uncovered the next. It's a common pattern late in a program.

43 · Taemin KoPlatform Framework

We could also catch this kind of leak much earlier with an automated memory check. If the nightly test suite folded the device a hundred times and compared system server memory before and after, a growth of one megabyte per fold would be impossible to miss. That test takes less than thirty minutes.

44 · Brian ShinPlatform Framework

I'd extend it beyond folding. Any repeated user action, like rotating the screen, switching apps, or connecting and disconnecting a charger, should have a simple before-and-after memory comparison. Most leaks are small per action and only become visible after hundreds of repetitions.

45 · Sarah LimProgram Management

Good. Let's add that to the retrospective list, and if it's really only thirty minutes, let's add the folding version to the nightly suite this week.

46 · Jisu HanDisplay Software

From the display side, I'd add the graphics buffer count to that check, not just total memory. Buffers are allocated in a separate pool, and on some builds they don't show up in the system server's memory numbers at all. If we only watch the system server, we could miss a buffer leak entirely.

47 · Taemin KoPlatform Framework

Good point. I'll include both numbers in the nightly report, with a simple threshold: if either grows by more than five percent over a hundred folds, the test fails and opens a ticket automatically.

Decisions and Action Items

48 · Sarah LimProgram Management

Let me summarize the plan. The managed leak fix goes into the factory build now, and the soak starts today. For the native leak: Hyemi runs the layer dump and the always-on display test today. If we have a fix by Friday the twenty-first, it goes into the factory build after a five-day soak. If not, it goes into the day-one update, which we plan from today, with the setup check. Option two, recreating the composition, is off the table. Any objections?

49 · Woojin ChoiDisplay Software

No objection. My team will support the layer analysis today, and Jisu can pair with Taemin on the fix if it turns out to involve the compositor.

50 · Sarah LimProgram Management

Thank you. Actions: Taemin merges the managed leak fix today. Hyemi runs the layer dump and the always-on test, with results by 2 p.m. Brian owns the native fix if it's in the always-on clock. Woojin and Jisu support the compositor side. Taemin adds the hundred-fold memory check to the nightly suite. And I'll brief the launch director this afternoon and start the day-one update plan as a precaution.

Closing and Next Checkpoint

51 · Sarah LimProgram Management

Thank you, everyone. We'll meet again today at 4 p.m. Korea time to review Hyemi's results, and then daily at 9 a.m. until the factory build is handed off on the twenty-eighth. I know daily meetings are a burden, but at this point in a launch, a day matters.

52 · Hyemi SongSQE

Understood. I'll post the layer dump in the launch channel the moment I have it.

53 · Taemin KoPlatform Framework

And I'll start reading the always-on clock code now, so I'm ready if the test confirms it. If it turns out to be somewhere else, I'll at least have ruled out one suspect before the four o'clock meeting.

54 · Brian ShinPlatform Framework

Thanks, everyone. Sarah, I'll join the launch director briefing if you want a framework voice in the room. Sometimes it helps to hear directly from the team that owns the fix.

증상

07 · Sarah LimProgram Management

혜미 님, 무엇을 발견했나요?

이제 로봇이 멈추지 않고 며칠씩 돌아가서, 처음으로 훨씬 느리게 진행되는 문제를 볼 수 있었습니다. 단말을 접거나 펼 때마다 시스템 서버 메모리가 약 1.2MB씩 늘어나고, 절대 줄어들지 않습니다. 약 2천 번 접으면 시스템 서버가 메모리 한계에 도달하고, 저메모리 킬러가 그걸 종료시켜서 단말이 소프트 리부트를 합니다. 화면이 꺼지고, 부팅 애니메이션이 나오고, 약 20초 만에 모든 게 재시작됩니다.

그리고 소프트 리부트는 사용자가 하던 작업을 잃게 만드는데, 리뷰어들이 장기 사용 리뷰에서 알아챌 겁니다. 멈춤만큼 극적이진 않지만, 제가 보기엔 출시 차단 이슈입니다.

지금까지의 힙 분석

12 · Sarah LimProgram Management

태민 님, 힙 덤프에는 뭐가 나오나요?

13 · Taemin KoPlatform Framework

사실 별개의 누수가 두 개 있고, 합쳐서 1.2MB가 됩니다. 첫 번째는 관리형 메모리, 즉 Java 힙에 있습니다. 접을 때마다 약 200KB입니다. 접을 때마다 메인 화면의 작업 표시줄 기능을 위한 새 설정 리스너가 생성되는데, 이전 리스너가 절대 해제되지 않습니다. 그래서 리스너가 수천 개 쌓이고, 각각 전체 디스플레이 설정 객체에 대한 참조를 붙잡고 있습니다.

14 · Brian ShinPlatform Framework

교과서적인 누수이고, 좋은 소식은 수정이 간단하다는 겁니다. 태민 님이 메인 디스플레이가 꺼질 때 리스너를 해제하는 패치를 이미 만들었습니다. 어제부터 로봇 두 대에서 테스트했는데 관리형 힙이 평탄하게 유지됩니다.

15 · Sarah LimProgram Management

두 번째 누수는요?

16 · Taemin KoPlatform Framework

두 번째는 네이티브 메모리에 있고, 더 큰 쪽입니다. 접을 때마다 약 1MB입니다. 힙 덤프 도구는 네이티브 할당을 그렇게 자세히 보여 주지 않지만, 볼 수 있는 건 접을 때마다 그래픽 버퍼 개수가 늘어난다는 겁니다. 커버 디스플레이가 꺼질 때 커버 화면을 그리는 데 쓰인 서피스가 완전히 해제되지 않는 것 같습니다.

네이티브 누수 범위 좁히기
