Analyzing a Use-After-Free Panic in the USB Gadget Path

USB 가젯 경로의 use-after-free 커널 패닉 분석

Orion에서 USB 테더링이나 파일 전송 중 케이블을 뽑을 때 드물게 커널 패닉이 발생합니다. SQE, 사내 커널·BSP 팀, Google 안드로이드 커널팀, 칩셋 벤더 Qorvix USB 팀이 KASAN 빌드로 확인한 use-after-free의 원인이 공통 커널 코드인지 벤더 드라이버인지 분석하고, 단일 패치 반영과 LTS 머지 중 대응 방안을 논의합니다.

Ken Tsai from Qorvix in Taipei. I maintain the USB controller driver for the Orion chipset.

05 · Hyunsoo BaeKernel & BSP

Hyunsoo Bae, also Kernel and BSP. I run our KASAN builds, so I'll walk through the report.

Symptom and Reproduction

06 · Tom AhnSQE

Here's the symptom. If a user is using USB tethering or transferring files to a computer, and they unplug the cable in the middle of a transfer, the phone occasionally panics and reboots. In the field, the rate is low, about two crashes per ten thousand unplugs, but because it happens to a lot of users every day, it's now the third most common kernel panic signature on Orion.

07 · Tom AhnSQE

To reproduce it in the lab, we built a simple rig with a relay that connects and disconnects the USB cable every few seconds while a large file transfer runs. With twenty devices running overnight, we get a crash roughly every two hours. That's slow, but it's enough to test hypotheses.

08 · Nathan BrooksGoogle Android Kernel Team

That's a very useful rig. Does it reproduce with tethering only, file transfer only, or does it need both?

09 · Tom AhnSQE

Either one is enough, but it's about three times more frequent when both are active at the same time. That's what made us suspect something shared between the two USB functions, rather than a bug in one of them.

Reading the KASAN Report

10 · Hyunsoo BaeKernel & BSP

The production dumps showed a crash in the completion callback of a USB request, with a pointer that looked like garbage. That's a classic sign of memory corruption, but it doesn't tell you who corrupted it. So we flashed the rig devices with a KASAN build. For anyone who hasn't used it: KASAN is the kernel address sanitizer. It tracks every allocation and every free, and when code touches memory that has already been freed, it stops immediately and prints a report.

11 · Hyunsoo BaeKernel & BSP

The KASAN report is very clear. It shows three stack traces. The first one is the bad access: the USB controller driver's interrupt handler calls the completion callback for a request. The second one shows where that request was allocated: by the tethering function when the cable was connected. And the third one shows where it was freed: by the same tethering function, in its disable path, which runs when the cable is unplugged.

12 · Jiwoo LeeKernel & BSP

So the sequence is: the cable is unplugged, the tethering function frees its request, and then, a moment later, the controller driver completes the same request and calls back into memory that no longer exists. It's very similar in shape to the storage bug: a completion arriving after the owner has already cleaned up.

13 · Tom AhnSQE

Then the question is whose responsibility it is to prevent that. Should the function wait for outstanding requests before freeing them, or should the controller driver make sure it never completes a request after the function is disabled?

14 · Nathan BrooksGoogle Android Kernel Team

According to the gadget framework's contract, it's a shared responsibility, but the order is clearly defined. When a function is disabled, it must first dequeue all its outstanding requests from the controller. Dequeue is supposed to be synchronous: when it returns, the controller has either completed the request with a cancellation status or guaranteed it never will. Only after that can the function free the memory.

15 · Ken TsaiQorvix USB Engineering

And our controller driver does implement dequeue that way, synchronously. So if the function calls dequeue before freeing, this shouldn't happen from our side.

16 · Hyunsoo BaeKernel & BSP

That's where it gets interesting. The tethering function does call dequeue, but only for requests on the receive endpoint. For the transmit endpoint, it relies on a disconnect callback from the controller to clean up. And the timing of that callback relative to disable is where the race happens.

Common Code or Vendor Code

17 · Tom AhnSQE

So is this a bug in the common tethering function, which is Google's code, or in how Qorvix's driver delivers the disconnect callback?

18 · Nathan BrooksGoogle Android Kernel Team

I looked at this before the call, and I believe it's in the common code. The transmit path in that function makes an assumption that held true for older controller drivers, but isn't guaranteed by the framework. In fact, a fix was merged into the upstream long-term stable branch for 6.1 about three weeks ago. Another partner reported a similar crash on a different chipset.

19 · Jiwoo LeeKernel & BSP

Three weeks ago. That explains why we don't have it. Our Orion kernel is based on the 6.1 stable release from three months ago. We merge stable updates quarterly, and the next merge isn't scheduled until October.

20 · Ken TsaiQorvix USB Engineering

I'm relieved, honestly. But to be thorough, I'll still review our controller driver's disconnect path. If our timing makes the race more likely than on other chipsets, I'd like to know.

21 · Nathan BrooksGoogle Android Kernel Team

That's a good idea. On the other partner's chipset, the crash rate was about ten times lower than what you're describing. So your controller may be completing transmit requests more quickly after disconnect, which widens the window.

Verifying the Upstream Fix

22 · Tom AhnSQE

Before we decide anything, I want proof that the upstream fix actually solves our problem. How quickly can we test it?

23 · Hyunsoo BaeKernel & BSP

The patch is small, about fifteen lines, and it applies cleanly to our tree. I can have a KASAN build with the fix on the rig this afternoon. If we run twenty devices for forty-eight hours, which would normally produce about twenty-four crashes, and we see zero KASAN reports, I'd consider that strong evidence.

24 · Jiwoo LeeKernel & BSP

I'd also run a non-KASAN build in parallel. KASAN changes timing, because every memory access is slower. Occasionally, a race disappears under KASAN simply because everything is slower, not because it's fixed. Testing both builds protects us from fooling ourselves.

25 · Tom AhnSQE

Good point. I'll split the rig: ten devices with KASAN plus the fix, ten with the production configuration plus the fix. And I'll keep a few on the old build as a control, just like we did for storage.

Field Impact and Interim Options

26 · Tom AhnSQE

While we wait for the test results, let's think about the users who are hitting this today. Even if the fix goes into the September build, it won't reach most devices until mid-September. Is there anything we can do in the meantime?

27 · Hyunsoo BaeKernel & BSP

Unfortunately, there's no configuration switch that avoids the race. The tethering function is either enabled or not, and disabling USB tethering entirely would be far worse than an occasional crash. The only real fix is the code change.

28 · Jiwoo LeeKernel & BSP

For context on severity, the panic doesn't cause any data loss, because file transfers over USB are written by the computer, not the phone, and an interrupted transfer simply fails. The user loses about a minute while the phone reboots. It's annoying, but it's not dangerous. So I don't think it justifies an emergency release outside the normal monthly schedule.

29 · Tom AhnSQE

Cherry-Pick or Stable Merge

Even though stable patches are generally safe, taking four hundred of them three days before a cutoff, with a critical security fix and a camera fix already in the same build, is too much change at once.

Merging stable updates only once a quarter means you're always up to three months behind on fixes like this one, including security fixes that don't get a separate bulletin entry. The partners with the fewest field crashes tend to merge stable updates monthly.

37 · Hyunsoo BaeKernel & BSP

Monthly merges sound good in theory, but each merge needs a full kernel regression cycle. With our current test capacity, monthly would mean SQE spends a quarter of its kernel time just validating stable merges.

38 · Tom AhnSQE

Open Questions

40 · Ken TsaiQorvix USB Engineering

One question for Nathan. If our controller completes requests faster than others, is that something we should change? I don't want to slow down our driver just to hide a race in a function driver.

증상과 재현

06 · Tom AhnSQE

증상은 이렇습니다. 사용자가 USB 테더링을 쓰거나 컴퓨터로 파일을 전송하다가 전송 도중 케이블을 뽑으면, 폰이 가끔 패닉을 일으키고 재부팅됩니다. 시장에서 비율은 낮아서 케이블을 만 번 뽑을 때 두 번 정도 크래시가 나지만, 매일 많은 사용자에게 일어나기 때문에 지금 Orion에서 세 번째로 흔한 커널 패닉 시그니처입니다.

07 · Tom AhnSQE

랩에서 재현하려고, 대용량 파일 전송이 진행되는 동안 몇 초마다 USB 케이블을 연결했다 끊는 릴레이로 간단한 장치를 만들었습니다. 단말 20대로 밤새 돌리면 대략 2시간마다 크래시가 납니다. 느리지만 가설을 테스트하기에는 충분합니다.

08 · Nathan BrooksGoogle Android Kernel Team

아주 유용한 장치네요. 테더링만으로 재현되나요, 파일 전송만으로 재현되나요, 아니면 둘 다 필요한가요?

09 · Tom AhnSQE

둘 중 하나만으로도 충분하지만, 둘이 동시에 활성화되면 약 세 배 더 자주 발생합니다. 그래서 두 USB 기능 중 하나의 버그라기보다 둘이 공유하는 무언가를 의심하게 됐습니다.

KASAN 보고서 읽기

10 · Hyunsoo BaeKernel & BSP

양산 덤프에서는 USB 요청의 완료 콜백에서 쓰레기 값처럼 보이는 포인터와 함께 크래시가 났습니다. 메모리 손상의 전형적인 징후지만, 누가 손상시켰는지는 알려 주지 않습니다. 그래서 장치에 연결된 단말에 KASAN 빌드를 플래싱했습니다. 안 써 보신 분들을 위해 설명하면, KASAN은 커널 주소 새니타이저입니다. 모든 할당과 해제를 추적하고, 코드가 이미 해제된 메모리를 건드리면 즉시 멈추고 보고서를 출력합니다.

11 · Hyunsoo BaeKernel & BSP

KASAN 보고서는 아주 명확합니다. 스택 트레이스가 세 개 나옵니다. 첫 번째는 잘못된 접근인데, USB 컨트롤러 드라이버의 인터럽트 핸들러가 요청의 완료 콜백을 호출하는 부분입니다. 두 번째는 그 요청이 어디서 할당됐는지 보여 주는데, 케이블이 연결될 때 테더링 기능이 할당했습니다. 세 번째는 어디서 해제됐는지 보여 주는데, 같은 테더링 기능이 케이블을 뽑을 때 실행되는 비활성화 경로에서 해제했습니다.

12 · Jiwoo LeeKernel & BSP

그러니까 순서는 이렇습니다. 케이블이 뽑히고, 테더링 기능이 요청을 해제하고, 잠시 후 컨트롤러 드라이버가 같은 요청을 완료 처리하면서 더 이상 존재하지 않는 메모리로 콜백을 호출하는 거죠. 스토리지 버그와 모양이 아주 비슷합니다. 소유자가 이미 정리한 후에 완료가 도착하는 거요.

13 · Tom AhnSQE

그럼 질문은 그걸 막는 게 누구의 책임이냐는 거네요. 기능 쪽이 해제하기 전에 미처리 요청을 기다려야 하나요, 아니면 컨트롤러 드라이버가 기능이 비활성화된 후에는 절대 요청을 완료 처리하지 않도록 해야 하나요?

14 · Nathan BrooksGoogle Android Kernel Team

가젯 프레임워크의 계약에 따르면 공동 책임이지만, 순서는 명확히 정의돼 있습니다. 기능이 비활성화될 때는 먼저 컨트롤러에서 미처리 요청을 모두 dequeue해야 합니다. dequeue는 동기적이어야 합니다. 반환될 때 컨트롤러는 그 요청을 취소 상태로 완료했거나, 절대 완료하지 않을 거라고 보장한 상태여야 하죠. 그 이후에야 기능이 메모리를 해제할 수 있습니다.

15 · Ken TsaiQorvix USB Engineering

그리고 저희 컨트롤러 드라이버는 dequeue를 그렇게 동기적으로 구현하고 있습니다. 그러니 기능이 해제 전에 dequeue를 호출한다면, 저희 쪽에서 이런 일이 생겨선 안 됩니다.

16 · Hyunsoo BaeKernel & BSP

거기서부터가 흥미롭습니다. 테더링 기능은 dequeue를 호출하긴 하지만, 수신 엔드포인트의 요청에 대해서만 합니다. 송신 엔드포인트는 정리를 위해 컨트롤러의 연결 해제 콜백에 의존합니다. 그리고 비활성화 대비 그 콜백의 타이밍에서 경쟁 상태가 생깁니다.

공통 코드인가, 벤더 코드인가

17 · Tom AhnSQE

그럼 이건 Google 코드인 공통 테더링 기능의 버그인가요, 아니면 Qorvix 드라이버가 연결 해제 콜백을 전달하는 방식의 문제인가요?

18 · Nathan BrooksGoogle Android Kernel Team

회의 전에 살펴봤는데, 공통 코드에 있다고 봅니다. 그 기능의 송신 경로는 예전 컨트롤러 드라이버에서는 맞았지만 프레임워크가 보장하지는 않는 가정을 하고 있습니다. 실제로 약 3주 전에 6.1 업스트림 장기 안정 브랜치에 수정이 머지됐습니다. 다른 파트너가 다른 칩셋에서 비슷한 크래시를 보고했거든요.

19 · Jiwoo LeeKernel & BSP
