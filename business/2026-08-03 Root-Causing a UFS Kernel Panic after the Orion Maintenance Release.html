Root-Causing a UFS Kernel Panic after the Orion Maintenance Release

Orion 유지보수 릴리스 이후 UFS 커널 패닉 원인 분석

Symptom and Reproduction Data

08 · Tom AhnSQE

Sure. The build is ORN.2.1.0, which went to our lab on July 28th. We run a 72-hour stress profile on two hundred devices: heavy file I/O, camera recording, app installs, and frequent screen on and off cycles. Over the first run, eleven devices hit a kernel panic, which is a rate of five and a half percent per 72 hours. On the previous release, 2.0.3, we had zero panics on the same profile.

09 · Jiwoo LeeKernel Storage

Just to clarify, are all eleven panics the same signature, or are we looking at several different crashes that happen to show up together?

10 · Tom AhnSQE

Good question. Nine of the eleven have the same signature: a NULL pointer dereference in the UFS completion handler, specifically in the function that completes a request after the controller signals it's done. The other two are different; one is a watchdog bite in the display driver and one is an out-of-memory panic. I'd treat those two as separate issues for now.

11 · Minji SeoSQE

Agreed. Let's park those two and focus on the nine. Tom, is there any pattern in when they happen?

12 · Tom AhnSQE

There is. In seven of the nine, the panic happens within two seconds of the screen turning off, while there's still heavy write traffic in flight. In the other two, the logs are truncated, so we can't say for sure. We also noticed that all nine devices have the same storage firmware version, which is the new one from Kestrel. But to be fair, every device in this run has that firmware, so that alone doesn't prove anything.

13 · Stefan BrandtKestrel Memory

Thank you for saying that, Tom. I'd just like to add that the new firmware has been in mass production with two other customers since May, with no reports of this kind of crash. That's not proof either, but it's a data point.

Ramdump Analysis and Hypotheses

14 · Minji SeoSQE

Jiwoo, you've been in the dumps all weekend. What does the analysis tell us so far?

15 · Jiwoo LeeKernel Storage

Here's what I can say with confidence. In all nine dumps, the completion handler is processing a request whose tag has already been released. In other words, the controller tells us request number seventeen is done, but by the time we look it up, slot seventeen is empty. The pointer we dereference is the request structure for that empty slot, which is why we get a NULL pointer.

16 · Laura ChenQorvix Customer Engineering

So it's a double completion, or at least a completion arriving after the request was already cleaned up. Do you know who released the tag first?

17 · Jiwoo LeeKernel Storage

That's the key question, and I don't have a definitive answer yet. What I can see is that in six of the nine dumps, the UFS error handler ran within the previous few hundred milliseconds. The error handler aborts outstanding requests and releases their tags. So my working hypothesis is a race: the error handler aborts request seventeen and frees the slot, and then a late completion interrupt for the same request arrives from the controller.

18 · Hyunsoo BaeKernel Storage

And that would explain the screen-off timing. When the screen turns off, we start the runtime suspend sequence for storage. If there's heavy write traffic, the suspend request has to wait, and if it waits too long, it times out. That timeout is one of the triggers for the error handler. So the chain would be: screen off, suspend attempt, timeout, error handler, abort, and then a late completion hits an empty slot.

19 · Minji SeoSQE

That's a plausible chain. But why would it start in 2.1.0? What changed in that path?

20 · Jiwoo LeeKernel Storage

Two things changed. On the kernel side, we merged a patch that shortened the suspend timeout from five hundred milliseconds to two hundred, to improve standby battery life. And on the firmware side, Kestrel's update enabled a larger write buffer, which means the device can take longer to flush data before it's ready to suspend.

21 · Stefan BrandtKestrel Memory

I'd push back slightly on the framing there. A larger write buffer does increase the worst-case flush time, that's true, but it's still well within the specification. According to the standard, the host is supposed to tolerate flush times of up to one second in that state. If the kernel gives up after two hundred milliseconds, I'd argue that's a host-side timing issue rather than a firmware problem.

22 · Hyunsoo BaeKernel Storage

That's a fair point about the timeout, and honestly, I was the one who proposed the shorter value. In our testing with the old firmware, flushes never took more than eighty milliseconds, so two hundred looked very safe. We clearly didn't retest it with the new firmware. That's on us.

23 · Laura ChenQorvix Customer Engineering

Let me add one thing from the controller side, because I don't think the timeout is the whole story. Even if the timeout is too short, the driver should never crash because of a late completion. The host controller can legitimately report a completion for a request that the software has already aborted. The completion path needs to check whether the tag is still valid before using it. If it doesn't, that's a robustness bug in the driver, regardless of the timing.

24 · Jiwoo LeeKernel Storage

I agree with Laura. We may have two problems layered on top of each other: a timeout that's too aggressive, which makes the error handler run far more often, and a missing validity check, which turns a recoverable situation into a panic. Even if we fix the timeout, I'd want the validity check in place, because there are other ways to trigger the error handler.
